# DNS under Russian network restrictions — August 29, 2026

This is a dated DNS review and reconfiguration guide. It is **not** an Xrayebator release note or
repair skill. The HAPP profile invariants below apply whether the profile was generated by
Xrayebator, another subscription provider, or the user, as long as the profile exposes equivalent
routing and DNS controls. Xrayebator 3.0 is used as a worked, source-verifiable example.

For installing and operating Xrayebator itself, retrieve the separate `xrayebator` skill.

The review was checked on **2026-08-29** against August measurements and Xrayebator `main` at
[`7df2381`](https://github.com/howdeploy/Xrayebator/commit/7df2381ce2427378e80e4e2fbc74f801d83a6795).
Filtering differs by operator and can change without a client update, so re-check the dated sources
before applying this runbook later.

> **Scope.** Work only on systems and connections the user is authorised to operate. Do not weaken
> corporate DNS or monitoring policy without the system owner's approval.

## Privacy boundary for the agent

Treat connection material as secrets. Do not ask the user to paste or publish:

- subscription URLs, QR codes, tokens, keys, or exported client JSON;
- server addresses, domains, resolver bootstrap addresses, or routing-profile names;
- unredacted service logs, DNS output, or packet captures.

Inspect those values locally over an authorised session and report only state such as “the managed
profile refreshed”, “no plaintext DNS packet was observed”, or “the resolver connection bypasses
TUN”. Never put private values into an issue, chat, screenshot, or this guide.

## Threat model — Russia, August 2026

As of 2026-08-29, assume all three conditions below can occur:

1. **Open DNS can be redirected or forged.** Measurements published on 2026-08-28 showed selected
   UDP/53 queries sent to public resolvers receiving authoritative-looking `NXDOMAIN` answers.
   TCP/53 reached the intended resolver in that measurement. This is evidence for those networks
   and timestamps, not proof of one nationwide rule.
2. **A public encrypted resolver can be blocked before DNS is exchanged.** August field reports
   describe direct DoH and DoT connections stalling or being reset during TLS setup. Results varied
   by operator, region, resolver, address family, and day.
3. **Correct DNS alone does not bypass later filtering.** DoH protects the query on its path to the
   resolver, but a direct application connection can still expose destination metadata or TLS SNI.

The stable design target is therefore narrower than “change resolver”: **the DNS transport must be
captured by the same working full tunnel as public application traffic**.

```text
application
    ↓
operating-system DNS + HAPP TUN
    ↓
HAPP profile with Global Proxy
    ↓
working full-tunnel route (VLESS + REALITY in the example)
    ↓
VPS outside the filtered access network
    ↓
authenticated DoH resolver
```

On this path the access ISP sees the tunnel flow, not a separate open DNS exchange or a direct TLS
session to a public resolver. The VPS operator and the chosen resolver remain in the trust model:
the resolver can see queries, and the VPS can observe destination metadata.

## Safe HAPP profile invariants

Verify behaviour rather than copying somebody else's JSON or private values:

- **Global Proxy is enabled.** Public application traffic and the DoH connection use the tunnel.
- Both **remote DNS** and **domestic DNS** use authenticated DoH. A provider-DNS or open-UDP
  fallback is not left enabled merely because it answers faster.
- The DoH hostname has a locally stored **bootstrap address** and a matching host override. This
  breaks the first-lookup cycle without consulting the access provider.
- Direct destinations contain only local, private, link-local, multicast, and other host-network
  ranges required to reach the LAN. Public domains, public resolvers, and country-wide public
  address sets do not bypass TUN.
- Domain strategy is `IPIfNonMatch`; FakeDNS is disabled for this managed DoH design.
- Geo databases are available through a route that can initialise without a direct blocked lookup.
  In the Xrayebator example they come from the authenticated HTTPS subscription origin.

A bootstrap entry alone is not sufficient. It avoids an open lookup of the resolver hostname, but
the resulting HTTPS connection must still enter TUN. If it leaves through the physical interface,
the endpoint remains visible and can be blocked.

The tunnel endpoint has its own bootstrap boundary. If its route depends on resolving a hostname
before TUN exists, keep an authorised out-of-band recovery path and a locally stored endpoint value.
Do not publish that value.

## Worked example — Xrayebator 3.0 and HAPP

At the reviewed commit, Xrayebator generates and schema-validates a complete managed HAPP routing
payload. It provides the invariants above: Global Proxy, DoH for both DNS classes, bootstrap and
host override, local-only direct ranges, protected geo downloads, `IPIfNonMatch`, and disabled
FakeDNS.

This is one implementation of the safe HAPP profile, not a claim that DNS hardening belongs only to
Xrayebator. A manually maintained profile or another subscription can implement the same design.

For an authorised existing Xrayebator installation:

1. Preserve SSH or another recovery channel that does not depend on the connection being changed.
2. Take a provider snapshot or another tested recovery point.
3. Update the project code and enter its menu so the current managed subscription and one-time
   migrations are applied:

   ```bash
   sudo xrayebator-update main
   sudo xrayebator
   ```

   The similarly named Xray-core-only update does not deliver project subscription changes.
4. Use HAPP **3.3.6 or newer**, fully stop stale HAPP cores, refresh the existing subscription, and
   reconnect once.
5. A locked Routing switch can be normal for a subscription-owned profile. Validate the generated
   settings; do not replace a complete managed payload with a rules-only fragment.

For another managed HAPP subscription, use its documented refresh/update path and verify the same
invariants. For a user-owned manual profile, change only the corresponding DNS and routing fields,
preserve a local backup, and avoid inserting any value copied from this example.

## Reconfiguration sequence for any HAPP profile

1. **Establish ownership.** Determine whether routing is managed by a subscription or editable by
   the user. Do not fight a locked provider-owned control.
2. **Preserve recovery.** Keep an independent access path and a local backup. Record no secret
   values in the work log.
3. **Update HAPP and stop stale cores.** A route latency check can be green while the main
   application TUN is down or an older process still owns traffic.
4. **Apply the invariants.** Refresh a managed profile from its trusted source or update the
   user-owned profile locally. Remove plaintext DNS and public direct-routing fallbacks.
5. **Reconnect once.** Confirm the main TUN, then wait for routing and geo assets to initialise.
6. **Run both leak checks and ordinary application checks below.** DNS answers alone are not proof
   that the resolver connection used TUN.

## Verification without disclosing connection data

### Plaintext DNS leak check

Identify the physical network interface locally. With HAPP TUN connected, observe only port 53:

```bash
sudo tcpdump -pni <physical-interface> 'udp port 53 or tcp port 53'
```

Trigger several uncached lookups through ordinary applications, then stop the capture. Report only
whether the packet count was zero. Do not paste the capture: a single line can expose queried names
and network addresses.

Expected result: **no port-53 packets on the physical interface**. If any appear, identify the
process or application bypassing TUN; choosing another open resolver does not fix the leak.

### Encrypted-resolver route check

Inspect physical-interface destinations locally while generating a fresh lookup. There must be no
direct connection to the configured DoH bootstrap destination. The only access-network flow for
that lookup should be the VPN transport. Report pass/fail only.

### Behaviour checks

- Resolve and open several ordinary domains through normal applications.
- Confirm subscription refresh and any required geo downloads succeed while connected.
- Test each access network the user actually relies on; operator behaviour is not uniform.
- If fail-closed behaviour is required, enable the operating system's kill switch only after
  explicit approval and test tunnel failure. A HAPP profile cannot guarantee that the client OS
  suppresses DNS after HAPP disconnects.

## Fallback order

1. **Full TUN with DNS inside the tunnel** — the required steady state.
2. **A private or low-profile DoH service on standard HTTPS, still inside the tunnel** — preserve
   certificate validation, bootstrap, Global Proxy, and the no-public-direct-rules invariant.
3. **Another working public DoH endpoint, still inside the tunnel** — direct availability is
   operator- and resolver-dependent, so today's success is not a durable property.
4. **TCP/53 only as a short diagnostic or emergency observation.** It is unencrypted and can be
   redirected once policy changes; never make it the steady-state configuration.

DoT and DoQ have distinct, easy-to-filter transports. They may be valid beyond the VPS, but do not
replace the client-side full-tunnel requirement.

## What does not solve the problem

- **Changing one open public resolver for another:** interception can follow the port or endpoint.
- **Enabling DNSSEC alone:** validation can reject forged data, but cannot recover the correct answer
  from a blocked path; safe failure is not connectivity.
- **Adding site addresses to a hosts file:** CDN addresses change and later IP/SNI filtering remains.
- **Browser-only DoH with public traffic outside TUN:** the later connection still exposes the
  destination and can be blocked.
- **Country-wide direct routing:** it returns public DNS and TLS decisions to the access ISP. Route
  only the minimum named local zones if split DNS is explicitly required and approved.

## Incident distinctions

- **Subscription refresh fails before TUN starts:** separate subscription-hostname bootstrap from
  in-tunnel DNS and use the authorised recovery path. Never send a secret URL to a public checker.
- **Routes look healthy but applications fail:** terminate stale cores, refresh the profile, confirm
  the main TUN, then inspect profile overrides and geo downloads.
- **DoH appears on the physical interface:** routing is bypassed. Repair Global Proxy/direct rules;
  correct DNS answers do not make this safe.
- **DoH fails only when TUN is on:** test resolver reachability from the VPS while preserving
  full-tunnel routing; distinguish VPS egress failure from a client leak.
- **A managed payload is rejected:** return to the provider's complete validated payload rather than
  forcing an incomplete custom fragment.
